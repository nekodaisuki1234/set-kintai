# 日別勤怠API・Excelテンプレート出力

A. Paper の日別記録と検証ルールを、AWSで動かすためのバックエンドです。同じリポジトリの `day-designs/paper-core.js` と `paper-holidays.js` を利用します。

このコードの追加だけではAWSリソースは作成されません。既存画面の保存先も引き続きブラウザのローカルストレージです。実際のAWS接続、Microsoft 365のログイン画面、既存データの移行はまだ行いません。

## モックを確認して確定した仕様

- 日別記録は出退勤、翌日退勤、休憩分数、勤務場所、作業内容、任意の複数フェーズ、休暇区分、代休元日、P1〜P4・SETの工数です。第5の工数は **SET** です。
- 実働・欠勤時間・有給取得数は記録から計算します。工数のAPI値は時間単位で、分単位に換算できる値だけを許可します。休憩時間の初期値は60分です。
- 出退勤・休憩の変更では、手動で割り振ったP2〜SETを維持してP1を調整します。退勤前やマイナス実働の保存を許可します。
- 編集画面に相当する全項目更新では、退勤入力済みで実働が0以上なら工数合計の一致を求めます。マイナス実働の保存は許可し、確認済み出力を止めます。
- 平日の実働4時間以下は有休・半休の登録を求めます。午前・午後半休を登録済みなら、この短時間チェックを免除します。8時間に足りないこと自体は欠勤時間の警告・集計の対象で、追加の提出エラーにはしません。
- 作業実績がある日の空白だけの作業内容、工数不一致、未入力・退勤未入力、マイナス実働などは、確認済み出力時に日付付きで返します。画面から渡された「検証済み」のフラグは信用しません。
- 土日・公式祝日に出退勤を登録すると休日出勤として扱います。「休日出勤」を選ぶ専用の区分はありません。休日出勤には「4時間以下なら有休」のチェックを適用しません。
- 代休は、実働が正の過去の休日出勤1日と、代休1日を紐付けます。半日分割はしません。同じ元日の二重利用、利用中の元日削除や実働をなくす変更を拒否します。
- 祝日データの収録範囲は `day-designs/paper-holidays.js` の `start` / `end` を参照します（現時点は2026〜2027年）。毎年3月の公式CSV更新workflowと手動更新手順は `day-designs/README.md` に記載しています。会社独自の休日カレンダーは未対応です。未収録の平日を含む期間は、確認済み出力を止めます。

モックの既存Excel出力は新しいブックを作る方式です。このバックエンドは、承認された `.xlsx` テンプレート、またはSET年度帳票の `.xlsm` を読み、対象の入力セルにデータを書きます。実際の会社テンプレート・社員の実績ファイルはリポジトリに含めません。A画面のAPI接続とAWS配置は別工程です。

## API

各ルートは、Microsoft Entra IDがこのAPI用に発行したアクセストークンを必要とします。API Gatewayでissuer・audience・有効期限・委任scopeを検証し、Lambdaも検証済みclaimsのtenant、社員object ID、scopeを確認します。社員は `tid` と `oid` から決まり、リクエスト本文で別の社員を指定できません。IDトークンや、別API用のアクセストークンは利用しません。

| Method / path | 内容 |
| --- | --- |
| `GET /v1/days?start=YYYY-MM-DD&end=YYYY-MM-DD` | 最大366日の日別記録、設定、更新番号、期間内の集計・未入力日を取得 |
| `PUT /v1/days/{day}` | 日別記録を全項目更新。完成済み・非負実働の工数合計を検証 |
| `PATCH /v1/days/{day}/time` | 出退勤・翌日退勤・休憩のみ変更。P1を自動調整し、他PJ工数を保持 |
| `DELETE /v1/days/{day}` | 日別記録を未入力に戻す。利用中の代休元日は削除不可 |
| `PUT /v1/config` | 勤務表設定・初期値を更新。社員情報と利用開始日は変更不可 |
| `POST /v1/exports` | 指定期間のExcelと出力時点のスナップショットを保存 |
| `GET /v1/exports/{id}` | 自分の出力記録に対する期限付き取得URLを再発行 |

更新処理は、取得時の `revision` を `expectedRevision` として渡します。同じ社員の記録・設定が別の操作で更新されていれば409で拒否します。画面側は再取得し、未保存の入力と変更内容を確認してから再送してください。

全項目更新の例です。

```json
{
  "expectedRevision": 7,
  "record": {
    "start": "09:00",
    "end": "18:00",
    "overnight": false,
    "breakMinutes": 60,
    "locationId": "place1",
    "note": "テスト対応",
    "phases": ["design", "test"],
    "leave": "",
    "sourceDay": "",
    "allocation": { "P1": 6, "P2": 2, "P3": 0, "P4": 0, "SET": 0 }
  }
}
```

`phases`は要件定義`requirements`、設計`design`、製造`implementation`、テスト`test`、運用`operations`、保守`maintenance`、調査`investigation`、その他`meeting`から複数選択できます。その他は保存済みの選択・初期値との互換性のため内部ID`meeting`を維持します。重複や未知のIDは拒否します。自由入力の`note`とは別に保存し、フェーズだけを選んでも作業内容の未入力チェックは免除しません。旧クライアントが`phases`を省略した場合は既存値を保持し、`[]`を明示すると全選択を解除します。古い記録にフィールドがなくても読み込めます。

時刻だけの変更例です。警告はレスポンスの `warnings` に返し、保存結果と分けます。

```json
{
  "expectedRevision": 8,
  "changes": { "end": "17:00", "breakMinutes": 60 }
}
```

`PUT /v1/config` は `expectedRevision`、`settings`、`defaults` を受け取ります。取得した設定一式を編集して返し、`settings.employee` と `settings.attendanceStartDay` は取得値を維持します。社員プロフィールは管理者が事前登録します。未登録の社員に架空データを自動作成しません。

`defaults.phases` は任意の初期フェーズ配列です。表示済みのIDのみ重複せず受け付け、省略した旧クライアントは保存済みの初期選択を保持し、`[]`で解除します。新しい日で日別`phases`を省略した場合は本人の初期フェーズを使い、既存の日は以前の選択を保持します。`defaults.note`と`settings.workSummary`は共通の作業概要として連動します。両方を別の値に変更した場合は`defaults.note`を優先します。初期値変更で既存の日別データは書き換えません。

全日の有給・公休・特別休暇・代休は、実働・欠勤・勤務日数は0、PJ別工数は全て0です。保存時に出勤・退勤時刻を空文字、翌日退勤をfalseにし、古い記録に残った時刻も取得・出力で空欄として扱います。全日休暇に正の工数を送ると422です。半休は実働を通常計算し、欠勤計算で4時間分の休暇を加算します。代休は元の休日出勤との一対一の検証も必要です。

Excel出力の例です。

```json
{
  "expectedRevision": 9,
  "period": { "start": "2026-10-01", "end": "2026-10-31" },
  "purpose": "checked"
}
```

- `checked`（省略時）: 共通検証に合格した記録だけを出力します。問題があれば422と日別の理由を返します。
- `review`: 確認用に出力し、検証結果を一緒に返します。検証済み・提出済みには扱いません。

このAPIは **Excel出力** です。メール送信・上長承認・正式な提出状態の確定は行いません。出力には取得元revision、期間、目的、検証結果、テンプレート版を保存します。レンダリング中に記録が変わった場合は出力確定を拒否し、成功URLを返しません。DynamoDBの応答が不明な場合は、確定済みデータを誤って消さず、出力番号で状態を再確認できるようにします。

## DynamoDBの持ち方

テーブルは1つで、社員ごとのパーティション内に日別アイテムを作ります。

| PK | SK | 内容 |
| --- | --- | --- |
| `T#{tid}#E#{oid}` | `REVISION` | 社員全体の更新番号 |
| 同上 | `CONFIG` | 社員情報、記録開始日、勤務表設定、初期値 |
| 同上 | `DAY#2026-10-28` | その日の記録 |
| 同上 | `COMP#2026-10-24` | 休日出勤日と利用先の代休日の対応 |
| 同上 | `EXPORT#{出力ID}` | 出力時のrevision、検証結果、S3保存先など |

日付範囲のQueryと、代休の関連日に絞った追加取得を使います。全社員をScanしません。代休の一意な紐付けと元日の変更は、更新番号を含むDynamoDBトランザクションで確定します。読み取りの前後で更新番号を確認し、異なる時点の記録を組み合わせないようにします。

設定を打刻のたびに再保存しないため、`CONFIG` と `REVISION` は別アイテムです。社員番号は業務情報、Entraの`oid`はアクセス範囲を決めるIDとして分けます。

## Excelテンプレート

テンプレートをそのまま読み込んでコピーし、[セル対応表の例](examples/template-mapping.example.json)で指定されたセルに書き込みます。この例のセル位置は説明用です。実テンプレートに合うことを確認してから利用してください。

version 1は従来の`.xlsx`向けです。主な設定は、対象シート、氏名・期間などの固定セル、日別行の開始位置と収容日数、各項目の列、合計のセルです。最大行数を超える期間、未知の項目、重複した出力先、既存の数式セルへの上書きなどは拒否します。指定していないセルやシートを意図的に書き換えません。

日別の列に任意の`phases`を指定すると、選択したフェーズを「設計・テスト」のような日本語で出力できます。列の指定を省略すれば、既存の会社テンプレートの列配置を保てます。`note`の本文にフェーズ名を自動挿入することはありません。

### SET年度帳票（.xlsm / version 2）

[SET帳票の設定例](examples/set-report-mapping.example.json)は、2026年4月〜2027年3月の月別シート、マスタ、36協定チェックシートを持つ帳票向けです。汎用マクロブックへの対応ではありません。`fiscalYear`と`closingDay`（31＝月末、15＝15日）を明示し、マスタB2の値が31/99または15で一致することを検査します。15日締めは前月16日〜当月15日です。全シートに影響するマスタの締日は出力時に変更せず、締日ごとに対応するテンプレートを用意します。

- 対象の1か月分に対応する月シートのみ、日別C/D/E（Excel時刻）、H/I（場所・内容）、J:N（P1〜P4・SET）、P（休暇区分）を書き換えます。翌日退勤は24時間を加算し、例として翌朝7:30を31:30で出力します。対象月のデータはアプリの記録を正とし、入力のない行は空にします。会社休日は日別の公休記録で表します。
- 共通項目は対象月のK1/L1（基準時間）、B42（共通概要）、C/Eの47〜51行（PJ情報）、B/C/Hの54〜56行（登録場所）だけ更新します。対象外の月のXML、VBA、スタイル、印刷設定の部品はそのまま保持します。
- フェーズ・午前/午後半休・代休元の日付は、日別I列のExcel「メモ」に付けます。既存の担当者メモを残し、`[SET勤怠の補足]`の区画だけ更新するため、再出力で重複しません。作業内容の本文は変えず、フェーズがあっても本文未入力を許可しません。メモはセルを選んで開きます。通常の印刷面に追加の列や文字は入りません。
- 数式の式そのものはすべて保持します。Node側では数式を計算しません。対象月と年間集計の古い計算キャッシュだけを無効化し、Excelで開いたときに自動再計算する設定にします。再計算機能のないプレビューでは計算結果が空欄の場合があります。Excel実機での再計算・メモ表示・印刷確認は本番切替前に行います。
- 氏名の既存数式を保持します。保存済みキャッシュの`#VALUE!`だけで表示不具合と判断しません。正しいファイル名でExcelを開いて正常表示される場合、氏名セルの修正は不要です。
- 欠勤・深夜・36協定の計算式は変更しません。欠勤と深夜の扱いは別途相談中です。

出力名は`作業報告書(YYYY年MM月)_氏名.xlsm`です。年月は締め対象月、氏名は認証された社員のプロフィールから決め、UTF-8のダウンロード名・マクロ用MIMEタイプで返します。

過去月が入った本人の帳票を継承する場合、`POST /v1/exports`に`baseExportId`を指定します。保存済みの本人の出力で、同じテンプレートID・版・年度の`.xlsm`に限定します。S3の保存ハッシュを照合してコピーし、対象月だけ差し替えます。元の出力ファイル・元の設定スナップショットは不変です。`baseExportId`を省略すると空の管理用テンプレートから作成します。最新設定から過去月を再生成しません。提出時の検証は今回の対象期間に適用し、以前の出力の検証結果は元の出力履歴に残ります。

```json
{
  "expectedRevision": 12,
  "period": { "start": "2026-10-01", "end": "2026-10-31" },
  "purpose": "checked",
  "baseExportId": "previous-export-id"
}
```

S3には次を非公開で置きます。

```text
templates/attendance.xlsx
templates/attendance.mapping.json
outputs/{tid}/{oid}/{exportId}.xlsx
outputs/{tid}/{oid}/{exportId}.snapshot.json
```

SET帳票の場合はテンプレート・出力の拡張子を`.xlsm`にします。実社員の過去帳票を全員共通のテンプレートには置かず、上記の本人限定の継承で扱います。

マッピングファイルは次の包み形式です。`mapping`にセル対応表を入れ、`templateSha256`で対応するテンプレートのバイト列を固定します。

```json
{
  "id": "attendance",
  "version": "2026-01",
  "templateSha256": "<xlsxファイルのSHA-256（64桁の16進数）>",
  "mapping": { "version": 1, "worksheet": "勤務表", "cells": {}, "days": {} }
}
```

上の`mapping`は構造の説明です。実際には例ファイルのように出力項目・日別行を設定してください。テンプレート未設定では出力を501で止め、代わりの様式を作って成功扱いにしません。S3の出力は固定の出力IDで保存し、取得URLは短時間のみ有効です。スナップショットには氏名や作業内容も含むため、AWSの権限管理・保存期間は本番運用前に決めます。

## ローカル確認

Node.js 24と、同梱の`package-lock.json`を使用します。

```sh
npm ci --prefix backend --ignore-scripts
npm test --prefix backend
```

メモリストア、DynamoDB/S3のテスト用クライアント、合成したExcelテンプレートで、社員間の分離、競合、代休、保存と出力の検証、テンプレートの保持・拒否条件を確認します。単体テストに実AWSアカウントやMicrosoft 365のトークンは必要ありません。

本番の`.xlsx`・`.xlsm`出力はJSZip 3.10.1とxmldom 0.9.12で必要なXMLだけを変更します。ExcelJS 4.4.0はテスト用ブックの作成・別の実装での読み取り検証にのみ使い、開発依存としています。本番のLambdaにはExcelJSと旧式のアーカイブ関連依存を含めません。テスト依存の`uuid`は11.1.1に固定しています。CIでブックの読み書きと本番依存関係の監査を行います。テンプレートは管理者が確認したファイルに限定し、利用者が任意のテンプレートやセル設定をアップロードするAPIはありません。

## AWSを用意する順番

[ローカルGitからAWSへ直接配置する手順](docs/aws-deployment.md)に、設定の保管場所、コミット前検査、SSOプロファイルと初回権限設定をまとめています。GitHubとAWSは認証連携せず、開発PCまたは配置用サーバーからAWS CLI／SAMで配置します。

1. AWS管理者がIAM Identity Centerの管理用・配置用SSO権限を準備します。
2. `deployment-bootstrap.yaml`で非公開の配置用S3、CloudFormation・Lambdaのロール、配置担当の管理ポリシーを作り、配置担当に割り当てます。外部IDプロバイダーやGitHub用ロールは作りません。
3. Git対象外の`deploy.local.json`にAWS・Entraの実設定を入れます。不足していればAWS接続前に停止します。
4. ローカルGitへコミットした版を、検査・ビルドして開発用AWSへ直接配置します。
5. 実テンプレートを非公開S3へ置き、実社員プロフィール・Microsoft 365ログイン・画面接続・実機とExcelの確認を進めます。

アプリのSAMテンプレートは`LambdaExecutionRoleArn`を必須とし、開発用の固定名リソースを使います。現在のテンプレートは`development`専用です。DynamoDBは従量課金・PITR・暗号化、S3は非公開・バージョニング・暗号化を設定し、スタック削除時も保持します。実AWSへの配置や画面の保存先切り替えは、構成ファイルの追加だけでは実行されません。

社員プロフィールは、実際のID・氏名・開始日を記載したJSONから明示的に作成します。以下の各値を実際の管理対象に置き換え、設定したAWS権限で実行します。既存プロフィールは上書きしません。履歴の自動インポートもしません。

```json
{
  "tenantId": "<Entra tenant UUID>",
  "employeeId": "<対象社員のEntra object UUID>",
  "attendanceStartDay": "2026-10-01",
  "employee": { "name": "<氏名>", "department": "<所属>", "id": "<社員番号>" }
}
```

```sh
AWS_REGION=ap-northeast-1 ATTENDANCE_TABLE=<テーブル名> ENTRA_TENANT_ID=<tenant UUID> npm run provision --prefix backend -- /安全な場所/profile.json
```

## フロント接続前・本番運用前に残るもの

現在の画面は月だけでなく、今期の有給、過去の未入力、グラフ、月をまたぐ代休も参照します。日別APIの1か月分をそのまま既存の全履歴に置き換えると集計を壊すため、必要な集計・関連日取得を含む接続方式を次段階で実装します。

Microsoft 365ログイン、社員の権限・退職時の扱い、既存データ移行、実テンプレート確認、会社独自休日、承認・締め後の修正、監査履歴、保存期間・復旧手順、正式な送付処理は別途必要です。今回の構成は、それらの会社ルールを推測して本番運用を開始するものではありません。

### フロントエンドの休暇申請プレビュー

A画面の休暇申請は現在ブラウザ内の記録のみで、管理者へは送信されません。共有コアは任意の`leaveRequests`履歴を検証できますが、このAPIには休暇通知・管理者宛先・受信箱のエンドポイントを追加していません。既存の日別PUT/PATCHは勤怠修正です。実際の通知は、AWS/APIと通知先を用意してから接続します。
